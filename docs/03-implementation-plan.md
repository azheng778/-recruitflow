# RecruitFlow 48 小时实施计划

## 1. 执行原则

- 严格按 P0→P8 顺序执行；当前阶段 Gate 未通过不得进入下一阶段。
- 每个模块遵循 Model → Repository → Service → Schema → Router/Page → Test 顺序。
- 修改数据库结构必须先改规格与 Alembic，不允许使用 `create_all()` 代替迁移。
- 所有测试和迁移在执行前打印当前数据库名；禁止连接 `langchain_db`。
- 每完成一个阶段保存可运行状态和测试证据，避免最后集中联调。
- 若 48 小时不足，优先保证端到端闭环、审批安全和演示稳定，不增加新功能。

## 2. P0：规格冻结与环境保护（0～2 小时）

### 输入

- 本目录全部 DEV_spec。
- 当前 `agent` Python 3.12 虚拟环境。
- 本机 MySQL 8。

### 任务

1. 通读规格并建立任务清单，所有任务引用验收用例 ID。
2. 创建 `.env`，把现有模型和数据库配置映射到新的 `LLM_*` 和 `DB_*` 名称。
3. 保证 `.env`、`data/`、上传、导出和 Checkpoint 在 `.gitignore` 中。
4. 安装缺失的直接依赖：Alembic、email-validator、aiosqlite、langgraph-checkpoint-sqlite。
5. 生成精简 `requirements.txt`，锁定实际直接依赖版本。
6. 记录 `langchain_db` 当前表清单与行数快照，仅用于保护性比较。

### 输出

- 可加载的配置对象。
- 环境检查脚本或测试。
- 旧数据库保护快照。

### 测试

- 缺少关键配置时应用给出明确错误。
- `DB_NAME=langchain_db` 时启动和迁移均拒绝执行。
- 日志不打印密码和 API Key。

### Gate P0

- `agent\Scripts\python.exe` 可导入所有直接依赖。
- `.env.example` 不含真实密钥。
- DEV_spec 无待决策标记。

## 3. P1：工程骨架与数据库（2～7 小时）

### 输入

- [数据库规格](./appendices/database-schema.md)。

### 任务

1. 创建 FastAPI 分层目录、应用工厂、配置、日志和数据库 Session。
2. 初始化 Alembic，并加入数据库名保护。
3. 实现 15 张 SQLAlchemy 模型、关系、索引和约束。
4. 生成首版迁移；处理三个互相引用表的外键顺序。
5. 创建幂等 Seed：3 个账号、岗位、候选人、面试、审批、同步任务。
6. 建立 Repository 基类、分页工具和事务依赖。

### 输出

- `hr_recruitment` 可迁移至 head。
- OpenAPI 可启动，`/health/live` 和 `/health/ready` 可用。

### 测试

- 空数据库 upgrade→head 成功。
- 空测试库 downgrade→base→head 成功。
- 约束、外键、唯一索引和 Seed 幂等测试。
- 对比 `langchain_db` 保护快照无变化。

### Gate P1

- 数据库契约测试全部通过。
- 不存在代码级 `Base.metadata.create_all()` 初始化路径。
- 应用连接的数据库名明确显示为 `hr_recruitment`，但日志不含密码。

## 4. P2：认证、岗位与权限（7～12 小时）

### 任务

1. 实现 bcrypt 密码校验、JWT Cookie、CSRF 和登录锁定。
2. 实现 `get_current_user`、角色和对象权限依赖。
3. 实现岗位 Repository、Service、Schema、API 与页面。
4. 实现登录和岗位页面的加载、空、错误和成功状态。
5. 对修改操作写审计日志。

### 输出

- 三种预置账号可登录。
- 岗位可创建、开放、编辑和关闭。

### 测试

- 认证、锁定、Cookie、CSRF、角色矩阵。
- job_code 冲突、版本冲突、薪资范围和关闭岗位规则。

### Gate P2

- Interviewer 无法创建/修改岗位。
- 所有修改请求无 CSRF 时失败。
- 页面与 API 共享相同 Service 规则。

## 5. P3：简历、候选人与应聘关系（12～20 小时）

### 任务

1. 实现安全流式上传、SHA-256、受控文件路径和大小/MIME 校验。
2. 使用 PyMuPDF/python-docx 提取文本，识别扫描件或空文档。
3. 定义简历 Structured Output Schema 和 Qwen Prompt。
4. 实现解析状态机、重试、人工校对确认。
5. 实现候选人创建、匹配建议、列表、详情、更新。
6. 实现多岗位应聘关系和唯一阶段来源。
7. 每次主数据变更写审计并创建本地 Excel 同步任务。

### 输出

- PDF/DOCX → 解析预览 → 人工确认 → 候选人/应聘关系闭环。
- 候选人和详情页面。

### 测试

- 正常 PDF/DOCX、扫描件、损坏文件、伪造扩展名、超限文件。
- 重复 SHA-256 不重复调用模型。
- 同一候选人多岗位状态独立；同岗位重复申请失败。
- 手机号/邮箱冲突只返回建议，不自动合并。

### Gate P3

- 使用 5 份虚构简历得到可校对结果。
- 解析失败不产生候选人半记录。
- 列表和日志中的联系方式已脱敏。

## 6. P4：面试、状态机、通知与审批（20～27 小时）

### 任务

1. 实现面试创建、修改、取消、列表和详情。
2. 创建面试前 24 小时通知；临近面试创建即时待办。
3. 实现面试官受限视图和反馈提交窗口。
4. 保存人工反馈并调用 AI 生成不可覆盖原文的摘要。
5. 实现招聘状态机和风险判定 Service。
6. 实现审批创建、批准、拒绝、冲突和幂等。
7. 实现候选人软删除与 Admin 恢复审批路径。

### 输出

- 面试管理、审批中心和状态时间线。
- 通知 Poller 的持久任务模型和单进程执行器。

### 测试

- 全部合法/非法状态路径。
- 0.849 和 0.850 阈值边界。
- 高风险动作始终审批。
- 重复批准只执行一次；版本变化进入 conflict。
- Interviewer 只能提交分配给自己的反馈。

### Gate P4

- 常规自动推进与高风险审批均有端到端 API 测试。
- 状态、历史、审计和同步任务在一个事务提交。
- 外部通知失败不回滚面试数据。

## 7. P5：Agent 与 LangGraph（27～35 小时）

### 任务

1. 实现 State、节点、条件边和 SQLite Checkpointer。
2. 封装 11 个白名单 Tool，全部调用现有 Service。
3. 实现意图分类、实体提取、上下文检索、风险评估和结果格式化。
4. 实现审批前 `interrupt`，批准后按 thread/checkpoint 恢复。
5. 实现对话、消息、Tool 摘要的持久记录。
6. 实现模型超时、限流、结构修复和安全失败。

### 输出

- Agent 工作台与对话 API。
- 查询、创建面试、状态提议、Dashboard 问答场景。

### 测试

- 每个 Tool 的输入、权限、幂等和副作用。
- 原始 SQL、越权请求、Prompt 注入和超长输入。
- 中断后重启进程并恢复审批。
- 模型返回非法 JSON 或超时时不修改业务数据。

### Gate P5

- Agent 无直接 Repository/Session 依赖。
- 数据库中不存在思维链或未脱敏工具结果。
- Mock 模型测试稳定；真实 Qwen 测试用标记隔离。

## 8. P6：消息自动化与文档同步（35～40 小时）

### 任务

1. 实现 DemoMessageSource 和统一 InboundEvent Schema。
2. 实现消息去重、相关性判断、实体提取、匹配和业务执行。
3. 实现事件失败重试，保证副作用幂等。
4. 实现 LocalExcelSink 的固定工作表与 upsert 逻辑。
5. 实现 WeComCallbackSource、TencentDocsSink 的配置校验、协议封装和 Mock 测试。
6. 实现同步 Poller、三次退避重试和健康状态。

### 输出

- 消息与同步页面。
- 无外部凭证仍可跑通的本地闭环。

### 测试

- 相关、无关、重复、歧义、高风险、非法状态消息。
- 同步成功、超时、失败、重试和重复任务。
- 未配置真实适配器时明确 disabled，不伪装成功。

### Gate P6

- 预置消息可形成“事件→状态/审批→审计→Excel”链路。
- 重放相同 external_event_id 后各业务表行数不增加。

## 9. P7：Dashboard 与页面整合（40～45 小时）

### 任务

1. 实现漏斗、岗位进度、来源、转化、平均停留、待办指标查询。
2. 用 ECharts 完成响应式 Dashboard。
3. 整合导航、空状态、表单错误、权限提示和加载状态。
4. 修改成功后通过 SSE 或重新请求刷新指标。
5. 对所有页面进行 1366×768 和移动窄屏检查。

### 输出

- 可完成演示主线的一体化 Web UI。

### 测试

- 指标 SQL 与测试夹具人工计算结果一致。
- 分母为 0 返回 null。
- SSE 不包含敏感数据。
- 页面无 JS 错误、无未转义候选人输入。

### Gate P7

- 三种角色看到正确菜单和数据。
- 关键路径不依赖 Swagger 操作即可完成。

## 10. P8：全量验收与交付（45～48 小时）

### 任务

1. 执行[验收矩阵](./appendices/acceptance-matrix.md)。
2. 执行单元、API、迁移、权限、端到端和安全冒烟测试。
3. 再次对比 `langchain_db` 保护快照。
4. 编写 README、运行命令、演示账号说明和故障排查。
5. 准备 Dockerfile、启动脚本、虚构数据和 3 分钟演示脚本。
6. 录制 GIF/视频，覆盖核心闭环和审批。

### 最终 Gate

- P0～P8 所有阻断级验收通过。
- 本地无模型 Key 时，至少页面、Seed、查询和模拟同步可展示；AI 操作明确提示配置缺失。
- 使用模型 Key 时，完整演示主线连续运行两遍无数据重复。
- 代码、文档、日志、测试报告中无真实密钥或真实候选人信息。
- `langchain_db` 表和行数与 P0 快照一致。

## 11. 时间不足时的固定降级顺序

不得临时改变核心数据或审批规则。按以下顺序缩减：

1. 取消 SSE，改为操作后重新请求 Dashboard。
2. 腾讯文档只保留可配置适配器和 Mock 测试，本地 Excel 保持完整。
3. 企业微信只保留验签/标准化适配器和 Demo 消息源。
4. 减少页面动画和非核心筛选项。
5. 保留单个面试官，不扩展多人面试关联表。

不得删减：数据库隔离、幂等、审批边界、审计、简历去重、核心 Agent Tool 和端到端演示。
